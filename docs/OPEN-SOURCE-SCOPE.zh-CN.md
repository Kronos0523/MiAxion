# 组件开放范围与后续计划

方向：开放 Bridge 公共代码与对外集成接口，包括通信协议、附属适配接口和示例。首批 SDK、协议与 NeoForge 只读示例随 v0.2.0 公开，见 [接收记录](SOURCE-INTEGRATION.zh-CN.md)。基础 Bridge 公共层及平台实现仍属于后续审查范围。

## 建议范围

| 部分 | 建议开放内容 | 导出前需要核对 |
|---|---|---|
| Bridge 公共层 | 对外集成所需的消息处理、能力注册及公共类型 | 是否依赖客户端内部项目；五端共用与平台差异 |
| 平台 Bridge | 经审查的各加载器适配代码 | 构建脚本、资源、运行依赖、第三方代码及声明 |
| 通信协议 | 消息结构、版本协商、错误语义、连接生命周期、脱敏示例 | 实际协议版本与实现一致，不含真实配对凭据 |
| 附属适配接口 | 接口定义、能力声明、注册机制、调用约定 | 接口能否独立构建，依赖是否允许分发 |
| 示例 | 最小连接、查询、附属实现与必要测试 | 只依赖公开接口，示例数据为虚构或可公开内容 |
| 桥接 skill | 接入步骤、公开 API 使用、附属开发与验证方法 | 从内部开发指导中拆出，去掉私有路径与内部流程 |

“所有接口”建议限定为第三方接入所需的对外合同。客户端内部模型编排、记忆、检索、内部管理和私有调试接口不随此方案自动公开。

## 发布前材料

每个组件都需有：精确源文件清单与来源提交、独立构建所需文件、直接及传递依赖、第三方许可原文与适用范围、组件许可证、构建与验证命令。缺少的材料明确待补，不以目录名推断开放边界。

导出采用选定提交的文件快照，不导入开发仓库完整历史。先在干净目录验证构建和示例，再进入 MiAxion 仓库。Gradle wrapper 等必要构建文件应逐项核准，不因全局忽略 JAR 而漏掉。

2026-10-26 用户已确定：自有 SDK、协议、示例和公开接入 skill 采用 MIT。现有公开 skill 的许可见 [组件 LICENSE](../skills/bridge-mod-integration/LICENSE)。SDK、协议和示例实际导出时，各自附带 MIT 正文并保留原作者署名；这项决定不等于候选文件已全部核准导出。

第三方代码、依赖和构建工具保留各自许可证与必要声明，不能改标 MIT。Bridge 公共层和平台实现继续按清单审查；本阶段不新增覆盖整个产品或全部仓库内容的 LICENSE。客户端、模型、知识内容、参考音频、语音包及演示素材不在上述 MIT 授权范围内。

## 明确保留在内部

客户端核心、模型编排、记忆和检索实现；开发仓库历史；真实密钥、配对凭据、数据库、用户 data、运行日志；内部交接、发布账号、私有调试资料及未核准的第三方素材。

GitHub 展示、用户文档和 Release 说明可以先准备。源码导出、推送、仓库公开与正式发版分别记录实际授权及完成状态。

## 桥接 skill 的拆分建议

已阅读开发仓库的 `bridge-mod-integration/SKILL.md` 与作者指南，并查看五份 references 的章节结构。它同时承担第三方接入指导和内部跨平台维护，建议提取独立公开版，内部完整版保留。

| 原有材料 | 公开版处理 |
|---|---|
| Skill 的边界选择、玩家请求示例、当前 API 能力说明 | 保留并指向公开仓库中的实际 SDK 与示例；只有对外文件齐备后才发布 |
| `addon-development.md` | 保留需求收集、最小 API、注册／生命周期、能力语义、交付规则；历史候选与内部交接链接改为经核对的公开兼容说明 |
| `extension-configuration.md` | 保留声明格式、身份与配置语义、支持的控件及使用边界；客户端内部实现追踪留在内部 |
| `integration-checklist.md` | 提取第三方必须遵守的线程、快照、取消、失效、资源与错误隔离规则 |
| `platform-sync-and-naming.md` | 保留新平台适配所需工具链、入口、打包资源和命名规则；只引用已公开模块，内部同步流程与历史发包记录留在内部 |
| `implementation-coverage.md` | 对外保留能力与平台范围、构建和实机验证的区分；内部客户端接线账本不整体导出 |
| 作者指南及其他引用文档 | 改写为仅依赖公开仓库的接入指南；清除私有历史设计、coordination 和内部测试目录引用 |

公开版需要独立闭环：外部作者只拿到公开仓库、SDK 和文档，也能构建示例。当前作者指南明确指出 `bridge-extension-example` 为 TestOnly，不能直接当正式附属模板；原文也依赖内部统一构建入口、Graphify 与私有客户端路径。这些都是不能原封不动公开整套 skill 的具体原因。

建议提供一个公开 skill，按“开发独立附属”和“移植基础 Bridge”两条路线导航；不要让第三方为了接入附属而修改客户端核心。公开协议应完整描述外部所需字段、生命周期、鉴权流程与错误语义，真实密钥、运行凭据和私有实现不随协议发布。

## 仓库放置建议

首期公开 skill 与协议、SDK、示例放在同一个 `agbushuo/MiAxion` 仓库。根 `skills/bridge-mod-integration/` 提供中文导航；`components/public-contracts/` 保留独立组件构建根、许可与随包 skill。实际状态见 [开发入口](BRIDGE-DEVELOPMENT.zh-CN.md)。公开接口变化时，同一提交更新 skill、示例和相关文档，发布时一起标明适配的 API 版本。

内部完整版仍保留在开发仓库，不与公开版做无审查的全量同步。只有当 skill 独立服务多个项目、出现独立维护团队或确需独立发行时，再考虑拆分仓库。当前不新增仓库。
